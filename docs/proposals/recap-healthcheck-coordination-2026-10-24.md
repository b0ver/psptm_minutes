# Предложение: согласовать healthcheck Recap с общим GPU-lock

Статус: подготовлено для решения владельца. В Recap не применено. Все его контейнеры и исходники сохранены.

## Проверенные факты

- Контейнер recap-stt-1 выполняет `python -m recap --smoke --only stt` каждые 120 секунд.
- Его `_check_stt` вызывает `registry.load_engine(settings)`. Проверка загружает модель в GPU даже при пустой очереди.
- Refusal текущего corpus в 22:02:47 МСК совпал с healthcheck 22:02:45.979-22:02:48.214. Compute PID698199 находился в точном Docker cgroup Recap STT.
- Отдельное пассивное наблюдение подтвердило следующий GPU PID716927 с точной командой этого healthcheck. Оно не запускало моделей.
- Поэтому очередь Recap может быть пустой во время его GPU-проверки. Наш read-only queue gate полезен для настоящих задач, но этот конфликт не устраняет.
- Наш main04 завершен: measure exit137, DB exit0, watchdog foreign_gpu_process. Первого полного примера нет. Данные, logs и dump сохранены на Bender.

## Подготовленная правка

Helper: `scripts/ops/recap_gpu_healthcheck.py`. Overlay: `docs/proposals/recap-stt-shared-gpu-healthcheck.yaml`.

Helper открывает существующий общий lock read-only. Он не создает новый файл и не принимает symlink. Он пробует взять exclusive flock без ожидания.

Если lock свободен, helper выполняет исходный GPU smoke через exec. Он сохраняет файловый дескриптор через exec. Поэтому lease остается удержанным до выхода настоящей GPU-проверки. Ошибка smoke сохраняет свой exit code. Она не превращается в успешную облегченную проверку.

Если lock занят, helper проверяет PID1 и read-only API Recap. Запрос имеет timeout3s и предел64KiB. При здоровых db/ollama он возвращает явный статус `gpu_readiness=deferred_shared_lock`. В этом состоянии проверена только liveness. Готовность CUDA отложена. После освобождения lock следующий штатный healthcheck снова выполняет полный GPU smoke.

Overlay закрепляет текущий image ID Recap. Он добавляет два read-only bind mount: helper и тот же inode общего lab.lock. Он заменяет только команду STT healthcheck. Исходники, модели, пароль, БД и настройки бота менять не требуется. Настоящие задачи Recap сохраняют приоритет через наш queue/GPU gate.

## Проверки до решения владельца

- Полный локальный Docker/PostgreSQL-набор: 375 passed за13.01s, одно предупреждение Starlette. Контейнеры и сеть удалены.
- Тест с реальным exec и синтетическим модулем доказал удержание flock до выхода smoke. Exit0/7 сохранены. При занятом lock модельный exec не выполняется.
- Проверены неизвестный lock, symlink, каталог, отказ CPU liveness и ограниченный HTTP-ответ.
- В отдельном CPU-only контейнере на Bender проверен read-only bind общего lock с текущим image/user Recap. Он видит занятую lease и может взять свободную exclusive lease. Inode, размер и mtime не менялись. GPU не использовался.
- Предложенная легкая проверка PID1/API прошла внутри текущего STT-контейнера без модели. Сервис не перезапускался.

## Условия применения после разрешения

1. Проверь точный CI helper.
2. Сохрани текущую конфигурацию и image ID Recap в защищенном каталоге.
3. Сравни текущую конфигурацию с конфигурацией запущенного сервиса.
4. Подготовь rollback той же конфигурации и image ID.
5. Согласуй краткое обслуживание STT по правилам проекта Recap.
6. Закрой прием по его runbook.
7. Дождись пустой очереди и отсутствия active leases.
8. Установи отдельную immutable копию helper с проверкой хеша.
9. Проверь, что bind mount указывает на тот же inode lock.
10. Примени overlay без сборки образа и без удаления данных.
11. Проверь PID1, API и healthcheck при свободном lock.
12. Проверь defer при занятом lock без запуска capacity-моделей.
13. Верни прием после проверки сервиса.
14. Только затем подготовь одну новую capacity-попытку.

Если конфигурация изменилась или безопасное обслуживание Recap не подготовлено, не пересоздавай сервис. Это предложение требует разрешения на изменение другого проекта. Оно не разрешает production delivery psptm_minutes.
