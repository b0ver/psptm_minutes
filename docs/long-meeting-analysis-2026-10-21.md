# Ограниченная обработка длинных встреч

Дата: 21 октября 2026. Реализация кандидата альфы; реальная GPU-приёмка ещё не выполнена. Причина изменения — [ошибка merge на 85-минутной записи](benchmarks/capacity-run-2026-10-14.md), а не подтверждённый предел длительности всех встреч.

## Поведение

Короткие реестры проходят прежнее семантическое сведение. Если полный вход merge либо промежуточный результат превышает бюджет, обработчик возвращается к исходным extract-частям. Он объединяет все категории механически, удаляя только полностью совпадающие записи. Модель сокращает только общий обзор; исходные обзоры и записи сохраняются отдельно. Проверка дословных цитат поручений/решений и очистка неподтверждённых авторов/сроков остаются обязательными: неподтверждённые пункты попадают в rejected_items, а не становятся проверенными.

Каждый запрос ограничен прежним бюджетом 45 000 символов system + user с учётом шаблона, служебных правил и JSON-экранирования. Это защитный символьный предел, а не измерение токенов или доказательство вместимости конкретного tokenizer. Лимиты модели num_ctx/num_predict и allowlist digest не меняются.

Общий обзор ограничен 6000 символами; prompt просит до 2500. Его вход делится на фрагменты, итог проверяется явно. Не более десяти раундов сведения; отсутствие сокращения даёт analysis_summary_not_reduced, пустой/слишком длинный ответ — analysis_summary_too_large. Эти ошибки не маскируются успешным результатом.

Большой отчёт тоже строится по частям с тем же бюджетом. Каждая запись передаётся целиком, без обрезания доказательной цитаты. Если одна запись или исходный обзор не помещается, возникает analysis_fact_too_large; чрезмерный служебный конверт даёт analysis_context_too_large. Список rejected_items не передаётся в отчёт. Полный текст конкретного отчёта сохраняется только после успеха всех его частей: ошибка поздней части не публикует половину отчёта. Уже готовые другие шаблоны остаются готовы. Проверенные facts сохраняются до render и используются при ручном повторе на той же версии источника.

В разделённом режиме нет семантического объединения дублей, отмен и смены статусов между частями. Каждый итоговый документ содержит предупреждение о сквозной проверке поручений/решений человеком; системная инструкция ограничивает вывод статусов переданной частью. Доставка реестра в prompt не доказывает полноту сформированного моделью Markdown. Такой результат остаётся черновиком, и качество нужно принять отдельно.

Версия анализа изменена на meeting-kit-v2-bounded-merge. При новой обработке несовпадающий source_hash сбрасывает facts/chunk_cache; старые готовые отчёты сами не перегенерируются. Для сравнения со старой версией используйте отдельную изолированную benchmark-БД, не редактируйте production-кэш. Схема БД не меняется.

## Локальная проверка

В изолированном Docker/PostgreSQL проверяются большой реестр всех категорий, точные цитаты, сохранение конфликтующих статусов, пять стандартных шаблонов, экранирование, рост промежуточного merge, ограничение раундов, атомарность сохранения отчёта и повтор из facts. Используются только синтетические данные и тестовая модель. Полный результат набора фиксируется в [статусе реализации](implementation-status.md).

## Следующая приёмка

1. Выделить отдельное окно общего GPU и повторить проверку свободных очередей/активных сессий непосредственно перед запуском. Не менять общую Ollama или модели.
2. В изолированном Docker-стенде с собственными БД/данными повторить corpus 30/60/85 минут на одном commit и разрешённом digest модели. Начать с ранее упавшей записи; затем проверить весь цикл STT → основной протокол → все пять отчётов.
3. Зафиксировать только безопасные агрегаты: итог, коды ошибок, длительности этапов, количество частей/пунктов/отчётов, точные commit/digest. Приватные входы и ответы модели остаются вне Git/CI artifacts.
4. Человеку проверить сохранение ключевых пунктов, доказательные цитаты, повторы и отменённые/изменённые поручения между частями. Сравнить с исходной записью и короткими контрольными примерами.
5. Только после успеха обновить оценку мощности по docs/capacity.md. Один успешный пример не доказывает устойчивую суточную квоту. Допуск staging/production отдельно по docs/ci-cd.md.
