# Telegram-интерфейс приложения: исследование и план

Дата: 8 октября 2026. Статус: предложение для реализации. Код бота, настройки окружения и работающие контейнеры в этом исследовании не изменялись. Токен не читался, обращения к боту и отправки сообщений не выполнялись.

## Рекомендация

Первый этап — обычный бот в личном чате владельца, меню и inline-кнопки, long polling. Он управляет существующим приложением и сообщает о готовности; PostgreSQL остаётся источником состояния. STT и разборы выполняются прежними локальными worker, бот сам не запускает модели. Mini App рассматриваем после работающих сценариев бота и решения о доступе к web-приложению с телефона.

Сохраняем действующую границу ADR 0001: записи, транскрипты и полные протоколы локальны, наружу передаются утверждённые карточки поручений. В рамках запрошенного интерфейса предлагаем добавить нейтральные статусы встреч и уведомления о готовности. Отдельно задан вопрос владельцу о брифах/отчётах в личном чате; до ответа это не считается разрешённой передачей. Передача файлов через Telegram также не подразумевается.

## Что уже реализовано

В app/telegram.py есть прямой HTTP-клиент Bot API через httpx, outbox доставки утверждённых поручений, ограниченные повторы, обработка двух кнопок «В работе»/«Выполнено». Callback проверяет числовые chat ID и user ID по allowlist; изменение статуса попадает в аудит локального реестра. BotCursor сохраняет offset обновлений; PostgreSQL advisory lock защищает от двух диспетчеров.

Действующие тесты покрывают запрет отправки до утверждения, отсутствие приватного содержимого в карточке, отказ чужому пользователю/чату, устойчивый offset, повтор callback и ограничение повторов доставки.

Пока отсутствуют /start и меню, обработка текстовых сообщений, список встреч, выбор 16 типов разборов, диалоги Телемоста, уведомления о готовности, обновление сообщения после изменения поручения, отдельные роли и маршрутизация уведомлений нескольким получателям. Получаются только callback_query, не message. Настройки рассчитаны на один чат доставки. Это основа доставки поручений, а не готовый интерфейс всего приложения.

## Предлагаемое меню

| Кнопка | Сценарий | Что отправляется в Telegram |
| --- | --- | --- |
| Встречи | Последние встречи, страницы по 5; открыть статус | Номер, дата, статус; название — только если выбран такой режим |
| Текущая обработка | Очередь, транскрибация, этап разбора, ошибка, неполная запись | Метаданные и понятное сообщение без диагностических деталей |
| Разборы | Для выбранной встречи выбрать типы и поставить задачу | Названия типов и состояние; текст результата зависит от режима данных |
| Поручения | Утверждённые, в работе, выполненные; фильтр | Только разрешённые карточки |
| Телемост | Ссылка → название → длительность → подтверждение записи → запуск | Управление и статус видимого ассистента |
| Открыть приложение | Загрузка записи, транскрипт, полный отчёт, проверка черновиков | Ссылка на доступный владельцу адрес приложения |
| Настройки | Уведомления, доступ и справка | Собственные настройки пользователя |

Команды-дубли: /start, /menu, /meetings, /status, /tasks, /telemost, /help, /cancel. Пользователь может проходить всё кнопками. На каждом экране нужны «Назад» и «Главное меню». /cancel завершает незаконченный диалог; остановка активной записи — отдельная команда с подтверждением.

Список типов берём из существующего каталога app.reports.catalog(), а не копируем в код бота. Пять универсальных типов отмечены по умолчанию. На небольшом экране показываем типы страницами, выбор отмечаем галочками, кнопка «Сформировать» создаёт задачу лишь после выбора. До появления транскрипта объясняем, что нужно дождаться обработки; существующий API сейчас возвращает 409 при раннем запросе разбора.

Статусы различаем: запись загружена; транскрибация готова; конкретные разборы готовы. ready встречи сейчас не означает готовности всех 16 разборов. У восстановленной части явно показываем неполноту; повторную передачу связываем с тем же UUID импорта, не создаём вторую встречу.

## Поручения

Карточка: текст, ответственный, срок, статус, стабильный ID и версия. Кнопки «В работе» и «Выполнено» меняют локальный реестр; после успешной транзакции обновляем карточку и клавиатуру. Просроченная версия кнопки приводит к обновлению карточки, а не к перезаписи новых данных. Права проверяем заново при каждом нажатии.

По действующей границе черновик и доказательная цитата остаются в web-интерфейсе. Утверждение выполняется там, затем отправляется утверждённый снимок карточки. Если позднее разрешим просмотр черновиков в личном чате, можно добавить подтверждение и редактирование в боте; это отдельное расширение режима данных. AI сам не утверждает и не рассылает поручения.

Первое подключение не должно внезапно рассылать накопленные старые pending-записи. Перед активацией нужно проверить их количество без вывода текста и определить стартовый диапазон доставки; старый outbox не удаляем и не помечаем отправленным без фактической доставки.

## Варианты интерфейса и ограничения Telegram

Обычный бот использует сообщения и callback. callback_data ограничен 64 байтами: в кнопке только короткая операция и идентификатор/версия, никаких текстов отчёта или секретов. Long polling и webhook взаимно исключают друг друга; первый этап использует polling. [Bot API](https://core.telegram.org/bots/api).

Стандартное скачивание ботом ограничено 20 МБ, отправка файлов ботом — 50 МБ. Для одного чата следует ограничивать частоту сообщений; Telegram рекомендует не превышать примерно одно сообщение в секунду. Прогресс обновляем в существующем сообщении при изменении этапа, а не отправляем новую строку на каждом проценте. Учитываем 429 и retry_after. [FAQ](https://core.telegram.org/bots/faq).

Локальный Bot API server снимает ограничение скачивания и допускает загрузку до 2000 МБ, но это не делает файлы в пользовательском чате локальными: пользователь всё равно передаёт материал в Telegram. Он сейчас не решает нашу задачу и не предлагается к установке. [Local Bot API server](https://core.telegram.org/bots/api#using-a-local-bot-api-server).

Mini App требует HTTPS-адреса. Backend проверяет подписанный initData, его возраст и разрешённый user ID; initDataUnsafe не является основанием для доступа. [WebAppInfo](https://core.telegram.org/bots/api#webappinfo), [проверка Mini App](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Это возможный второй этап: адаптировать имеющуюся web-форму под телефон и загружать файл непосредственно в наше приложение, а не сообщением боту. Однако доступ с телефона, TLS и доверие клиенту надо проверить отдельно. Существующий localhost:18191 — туннель на компьютере владельца; на телефоне localhost указывает на сам телефон. Саму Mini App нельзя обещать работающей на нынешнем HTTP-адресе.

## Реализация в проекте

Для MVP сохраняем имеющийся Python/httpx и Docker. Новая библиотека, Redis, публичный webhook и второй AI-контур не нужны. По мере расширения отделяем транспорт Bot API, обработчики меню, представление карточек и локальные операции в разные модули.

Бот вызывает те же операции предметной области, что web-интерфейс. Из API надо выделить общие функции чтения метаданных встреч, постановки разбора и работы с реестром: нельзя дублировать правила и нельзя выводить полный ответ meeting API в Telegram, поскольку он содержит транскрипт, протокол и доказательные цитаты. Для Телемоста — внутренний запрос к существующему агенту или API через Docker-сеть; стандартный URL агентом валидируется как раньше. Боту не нужен доступ к GPU, моделям или аудиофайлам.

Предлагаемые новые таблицы:

- TelegramDialog: user_id, chat_id, шаг диалога, выбранные ID/типы, срок действия, версия. Незавершённый выбор переживает рестарт и не сохраняется навсегда.
- TelegramOperation: уникальный update_id/callback ID, тип операции, локальный объект, состояние и результат. Долгие операции ставятся в очередь; cursor подтверждается после долговечного сохранения намерения, а не после неустойчивого сетевого запроса.
- TelegramNotification: уникальный ключ события, получатель, разрешённый снимок полезной нагрузки, состояние доставки, message_id, попытки и next_attempt. Не перегружаем существующий Outbox, который связан с action_id и уникальной парой action/version.

После рестарта повторное Telegram-обновление не создаёт новую встречу/разбор. Для запуска Телемоста потребуется отдельный идемпотентный ключ команды: текущий start отвергает занятость, но не предоставляет квитанцию ранее принятого запуска. Проверка одного занятого браузера сама по себе не решает потерянный ответ запуска.

В обработчике быстро отвечаем на callback, затем показываем результат. Повторяем сетевые операции отдельно от бизнес-транзакции. Потеря ответа sendMessage может привести к дублю: Bot API не даёт нам общего ключа идемпотентности отправки, поэтому exactly-once доставки не обещаем. Локальные изменения реестра при этом обязаны быть идемпотентными.

Получение Telegram-событий и отправка уведомлений не должны блокировать друг друга на 20-секундном long polling. Используем отдельные циклы/задачи с общим транспортом и одним владельцем cursor. Сохраняем singleton-lock. Нераспознанное сообщение от разрешённого пользователя возвращает меню; чужой запрос не получает список встреч или содержимое реестра.

## Доступ и конфигурация

Владелец создаёт бота. Для выбранного .env используем TELEGRAM_TOKEN; в реализации нужно добавить отдельный загрузчик Telegram-токена и пробросить переменную только контейнеру telegram. Функция app.settings.secret сейчас читает только *_FILE; Compose монтирует secrets/telegram_token. Простое добавление TELEGRAM_TOKEN в .env без изменения Compose/загрузчика не включит бота. Не меняем способ загрузки секрета PostgreSQL ради этой задачи.

Если выбран файл, сохраняем TELEGRAM_TOKEN_FILE. Если заданы оба источника, конфигурация должна явно выбрать один или завершиться понятной ошибкой; placeholder DISABLED не должен скрывать настоящий токен из .env. Токен не пишется в документы, callback, образ или журналы; HTTP-логирование URL Bot API отключено.

Переменные для подключения:

```dotenv
TELEGRAM_TOKEN=<заполняется владельцем в своём .env>
TELEGRAM_ENABLED=0
TELEGRAM_ALLOWED_USERS=<числовой Telegram user ID владельца>
TELEGRAM_CHAT_ID=<разрешённый чат доставки>
# Планируемые настройки, пока не читаются кодом:
TELEGRAM_DATA_MODE=control
TELEGRAM_APP_URL=<адрес приложения, доступный с нужного устройства>
```

Первый этап — личный чат владельца; публичные группы и каналы в маршрут не добавляем. Разрешение по числовому ID, не по username и не по признаку «первый написавший». Токен не заменяет allowlist пользователей. Начальный /start может помочь пользователю увидеть собственные ID, но не должен автоматически выдать ему доступ. Команду BotFather /setcommands можно выполнить при подключении; Mini App и inline mode сейчас не требуются.

Приватное приложение остаётся на текущем loopback-адресе. Если позже понадобится HTTPS-доступ из Mini App, сначала вводим проверяемую сессию и права на каждый маршрут, затем выбираем LAN/VPN/публичный доступ. Нельзя просто опубликовать нынешний API без авторизации: Origin guard не является проверкой личности.

## Порядок работ и критерии проверки

1. Поддержка .env токена, проверка конфигурации и личного доступа, /start и меню; синтетические тесты без Telegram.
2. Встречи, стадии обработки, выбор существующих типов разборов; PostgreSQL диалоги и операции, дедупликация команд.
3. Поручения, обновление карточки после действия, нейтральные уведомления о готовности, контролируемый старт outbox.
4. Управление Телемостом: разрешение записи, длительность, запуск, остановка, неполная запись и повтор импорта; дедупликация запуска.
5. Подключение созданного пользователем бота и тестовые сообщения в явно выбранном чате. Прежние AI worker продолжают работу; Telegram развёртывается отдельно.
6. Отдельное решение о брифах/отчётах и Mini App, если они нужны.

Тесты должны проверять чужой user/chat ID, истечение диалога, две одинаковые команды после рестарта, старую версию кнопки, потерянный ответ внешнего запроса, 429/retry_after, блокировку бота, отсутствие записей/цитат/протоколов в режиме control, раздельную готовность транскрипта и разборов. Первый реальный тест проводится на синтетическом поручении; очередь старых реальных поручений самопроизвольно не отправляется.

## Что понадобится от владельца

Сохранённый токен, username бота, разрешённый числовой user ID и выбор чата доставки; решение о содержимом сообщений. Для обычного меню домен и сертификат не нужны. Для открытия локальных материалов с телефона нужен отдельно доступный адрес приложения; для Mini App также HTTPS и проверка Telegram-сессии.
