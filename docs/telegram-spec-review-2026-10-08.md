# Дополнения из функциональной спецификации Telegram-бота

Дата: 8 октября 2026. Основание: приложенная владельцем спецификация «Telegram-бот сервиса записи встреч: ресерч и функциональная спецификация», версия 1. Это предложение к нашему плану, не утверждение всех решений вложения и не запуск описанных интеграций.

## Добавляем в первую реализацию

| Дополнение | Как адаптируем к нашему приложению | Проверка |
| --- | --- | --- |
| Вставка ссылки без /record | Авторизованный пользователь отправляет точную ссылку Телемоста. Показываем карточку настроек и кнопку запуска; сама вставка не включает запись. Используем серверный валидатор URL | Чужой пользователь, произвольный URL, повторное update, кнопка отмены |
| Одна обновляемая карточка | Храним session/meeting ID, chat ID, message ID и последнюю отрисованную версию. Правим статус при переходах; таймер — редко. Новое уведомление для допуска, сбоя и готовности, с подавлением повторов | message is not modified; удалённая карточка; блокировка бота; восстановление после рестарта |
| Содержательный статус | Допуск → штатная запись → файл принят → транскрипт готов → разборы готовы. Показываем неполноту, подтверждённые части и состояние их сохранения | uploaded/ready не объявляют все отчёты готовыми; частичный материал помечен |
| Шаблоны и готовность каждого | Список 16 существующих типов с отметками выбран/готовится/готов/ошибка. Выбор сохраняется в диалоге; задача создаётся отдельной кнопкой | Повторное нажатие не запускает второй разбор; ошибки отдельных типов не скрываются |
| Удобные поручения | Утверждённые, в работе, выполненные, просроченные, без срока; навигация по встрече | Даты учитывают выбранный часовой пояс; отсутствие исполнителя явно показано |
| Завершение диалога | Назад, Отмена, /cancel и /start, TTL черновика 15 минут как начальное предложение | /cancel не останавливает активную встречу; старое действие не воскресит черновик |
| Права и версии кнопок | Версия протокола callback плюс версия объекта/диалога, проверка user/chat и доступа к объекту при каждом нажатии | Копирование/пересылка карточки не выдаёт права; stale callback обновляет экран |
| Понятное восстановление | Отдельные действия: повторить передачу файла, обработать сохранённую часть, повторно подключить нового ассистента. Не объединяем всё кнопкой «Повторить» | Повтор импорта использует прежний UUID; новый вход требует явного действия |
| Настройки уведомлений | На первом этапе личный чат владельца; включение уведомлений о допуске, завершении и ошибке. Выбор типов по умолчанию | Изменение настройки не делает автоматическую рассылку старых материалов |

Кнопки primary/success/danger и disabled поддерживаются текущей документацией. Можно добавить оформление и обозначение недоступных действий, но смысл должен сохраняться в тексте без зависимости от цвета. Для disabled используем соответствующее API-поле, не притворяемся обычной callback-кнопкой. [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton).

## Следующий функциональный этап

**Разовое планирование.** Кнопки «Через 5/15/30 минут», точные дата и время, обязательный экран подтверждения с часовым поясом. Свободный русский текст — удобное дополнение после надёжного выбора времени; неоднозначный результат не запускает встречу сам. Приоритет кнопок выше, чем зависимость от dateparser.

Храним scheduled_join и отдельный occurrence с запланированным UTC-временем, владельцем, шаблонами, сроком допустимого опоздания, версией и ссылкой на run. Планировщик работает в Docker, выбирает задания из PostgreSQL, атомарно резервирует каждое выполнение и переживает рестарт. Политика пропуска важна: встреча, назначенная час назад, не должна внезапно начать записываться при подъёме сервера. Отмена и запуск конкурируют через блокировку/версию одного occurrence; отмена после запуска предлагает явную остановку.

**Конфликты расписания.** Сегодня один браузер обслуживает одну встречу. Если он занят, показываем конфликт до сохранения расписания и отдельно проверяем занятость в момент старта. Для неподтверждённой доступности не обещаем одновременную запись двух встреч. Масштабирование пула браузеров — самостоятельная серверная задача, STT-очередь остаётся отдельной.

**Повторы.** RRULE, исключение одного события, изменение только этого события или всей серии. UTC для фактического запуска, IANA timezone для календарного правила; ежедневная встреча в 09:00 должна следовать местному времени при сезонном изменении смещения. Одной UTC-строки для повторов недостаточно. Вход «за минуту» и допустимое опоздание — настройки, не гарантия попадания в комнату: допуск организатора остаётся обязательным.

**Доступ к задачам по исполнителю.** Сейчас owner — свободный текст. По нему нельзя автоматически выдать доступ к «моим» задачам или отправить их человеку. Нужен подтверждённый профиль и связь с Telegram user ID; спорное «Иван» остаётся не назначенным для маршрутизации. Отметка «Принял/Не моё» — отдельное состояние принятия назначения, а не замена approved/in_progress/done.

**Заметка к моменту.** Сохраняем текст как пользовательскую заметку с автором, временем получения, привязанной сессией и приблизительной позицией записи. Поздняя отправка может требовать ручного выбора таймкода. Пользовательская заметка не становится дословной цитатой из транскрипта, не доказывает принятое решение и не обязана создавать поручение. Сначала используем заметки в локальной карточке, затем — как явно обозначенный источник для локального разбора. Сам текст, введённый в Telegram, уже находится в этом внешнем канале.

**Вопросы к встрече.** В kit есть промпт 30_meeting_chat.md, но готового endpoint и очереди вопросов в приложении нет. Нужен отдельный локальный job: выбранная встреча, найденные сегменты, ответ с проверяемыми ссылками на источник, явное «в записи не найдено», отмена и ACL. Вывод ответа в Telegram зависит от выбранной границы данных. Стриминг добавляем после проверки источников и отмены; полезнее сначала корректный окончательный ответ с индикатором обработки.

**Поиск и дайджесты.** Начать с названия/даты и PostgreSQL, без новой векторной базы. Полнотекстовый поиск, вопросы и межвстречные дайджесты должны учитывать тот же доступ к исходным встречам. Наличие промпта 31_cross_meeting_digest.md не означает существования готового сервиса дайджестов. Точное расписание уведомлений задаёт пользователь; из примера «9:00/17:00» автоматизация не создаётся.

## Уточнения и исправления спецификации

1. **Outbox и «ровно один раз».** Уникальный ключ события предотвращает создание двух намерений отправки. Если Telegram принял sendMessage, но ответ потерян, повтор может создать второе сообщение. Утверждаем идемпотентность локальных операций, контролируемые повторы доставки и стабильные ID карточек; абсолютную exactly-once доставку не обещаем.
2. **Редактирование после 48 часов.** Это не общий запрет для всех сообщений бота. Документация ограничивает определённые business-сообщения, отправленные не ботом и без inline-клавиатуры. Для нашей собственной карточки используем edit; если она недоступна/удалена, создаём замену по фактическому отказу. [editMessageText](https://core.telegram.org/bots/api#editmessagetext).
3. **100 кнопок/8 в ряд.** В python-telegram-bot эти значения прямо обозначены недокументированными и изменяемыми. Это ориентир совместимости, не договор Telegram о неизменном лимите. Наш UX ограничиваем небольшими страницами и 1–2 длинными кнопками в ряд. [Константы библиотеки](https://github.com/python-telegram-bot/python-telegram-bot/blob/master/src/telegram/constants.py).
4. **login_url и Яндекс ID.** login_url относится к Telegram-аутентификации на сайте. Связь с Яндекс ID требует отдельного OAuth-процесса и проверки корпоративной принадлежности. Для персонального первого этапа корпоративная почта, SMTP и Directory API не нужны. [LoginUrl](https://core.telegram.org/bots/api#loginurl).
5. **Тишина и перезапуск захвата.** Ненулевые байты не доказывают речь, тишина не доказывает потерю звука. Различаем поступление фрагментов, состояние дорожек/рекордера и измеренный уровень. Не перезапускаем запись по одному порогу «две минуты тихо», не обходим отзыв разрешения записи. Сейчас capture_health сообщает о сохранении частей; live-уровень и актуальное число участников в публичном API ещё не реализованы.
6. **«Неготовый отчёт генерируется быстро через --only-render».** В нашем приложении используется reports.enqueue и общий analysis-worker, а не эта CLI-команда. Готовый текст можно отдать сразу, новый тип ставим в существующую очередь, при возможности используем кэш фактов. Мгновенная генерация и постоянное время не гарантируются.
7. **Дедупликация встреч.** Одну постоянную ссылку Телемоста используют для разных дней — мы уже повторно тестировали одну и ту же ссылку. Разделяем команду, серию, конкретное выполнение и сессию записи. Повтор update использует прежний ключ, новое явное выполнение получает новый ключ. Нельзя навсегда блокировать новые встречи по одному join_url; нельзя полагаться на уникальность NULL starts_at для немедленных запусков.
8. **Подписанная ссылка и доступ.** Подпись с TTL ограничивает время доступа, но не удостоверяет пользователя: ссылку можно переслать. Для привязки к конкретному владельцу нужны авторизация сессии и ACL на скачивание. Если в ссылке есть секретный параметр, не включаем его в лог. Пока внешний доступ к материалам не опубликован.
9. **Отправка исполнителям/почта/трекер.** Это самостоятельные операции с выбранными получателями и подтверждённым содержимым. Готовый AI-черновик сам их не запускает. Пользователю должно быть видно, какие карточки и куда уйдут; запрос на исследование их не разрешает.
10. **Готовность и состояние «звук есть».** Таймер карточки не подменяет фактическую длительность аудио. Наша последняя штатная и резервная запись содержала по 174,30 секунды; это проверили декодированием. Покрытие встреч в админке требует определённого набора ожидаемых встреч и критериев успешной записи, а не только числа finished-сессий.

## Что пока не переносим в инфраструктуру

Сохраняем Python/httpx, long polling, PostgreSQL и локальный volume. Для текущего персонального бота aiogram, Redis FSM, Celery/arq, MinIO, nginx/webhook, SMTP и local Bot API server не обязательны. Их можно выбирать по измеренной необходимости; планируем диалоги и задания так, чтобы менять транспорт независимо от бизнес-операций. Ресерч не является основанием установить весь предложенный стек.

Файлы DOCX/PDF/TXT/SRT, хранение file_id, выдача аудио/архивов и inline-публикация материалов рассматриваются после выбора режима данных. Local Bot API не делает сообщения и файлы локальными. До отдельного решения действует ADR 0001: записи и полные материалы остаются в приложении.

Топики в личке, Rich Messages и эфемерные групповые ответы документированы в актуальном API, но для первой версии достаточны обычные карточки. Проверим их на нужных пользователю клиентах позже; сохраняем возможность обычной личной навигации. [Изменения Bot API](https://core.telegram.org/bots/api-changelog).

Группы по умолчанию не получают материал и не становятся разрешённым адресатом из-за того, что там вызвали бота. Отчёт туда, где вызвали бота, — политика аналога, не наше принятое решение. Сначала личный чат владельца, затем подтверждённые пользователи/права на встречи.

## Дополнения к модели и тестам

К TelegramDialog/TelegramOperation/TelegramNotification из первоначального исследования добавляем TelegramMessage (объект, chat_id, message_id, kind, render_version, thread_id при необходимости). Не заводим параллельные tasks/reports вместо существующих Action/MeetingReport. Будущие Schedule/ScheduledOccurrence и UserIdentity добавляются миграциями; изменение уже имеющихся колонок нельзя выполнять через create_all.

Проверки дополнить сценариями: карточка удалена; пользователь заблокировал бота; отмена одновременно со стартом; два старта одной команды; новая встреча по прежней ссылке; два пользователя выбрали один временной слот; рестарт после пропущенного времени; повторяющаяся встреча на границе смены часового смещения; поиск не раскрывает чужой материал; пользовательская заметка не становится доказательной цитатой; отправка группы без явно выбранного маршрута запрещена.

Результат: UX спецификации используем как основу, расширения разбиты на этапы, инфраструктура и граница передачи данных выбираются по нашему проекту. Реализация бота ещё не начата.
