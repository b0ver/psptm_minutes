# Правила разработки и выпуска psptm_minutes

- Рабочий код и документы ведём в этом репозитории; текущее заключение об альфе: `docs/alpha-readiness-2026-10-13.md`, эксплуатация и доставка: `docs/ci-cd.md`, мощность: `docs/capacity.md`.
- Перед изменениями смотреть `git status`; сохранять чужие незакоммиченные изменения. Не включать лабораторные эксперименты в production без отдельной оценки качества и подтверждённой модели/digest.
- Приложение и тесты запускать в Docker. PostgreSQL тестов из `compose.test.yaml` изолирован; не запускать pytest против рабочей БД: fixture выполняет TRUNCATE.
- Для изменений поведения запускать 150+ integration-тестов: `docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests`, затем `docker compose -f compose.test.yaml down`. Изменения эксплуатационных инструментов проверять соответствующими тестами и синтаксисом.
- Не выводить .env, secrets, полные inspect/environment, транскрипты и ответы AI. Не сохранять пользовательские записи/метрики с приватным содержимым в Git, CI logs или artifacts. Для статуса использовать агрегаты и безопасные коды.
- Корпоративный пилот: Telegram allowlist, web только loopback/SSH; открытие общего web требует авторизации и серверного ACL. AI-результат остаётся черновиком; поручения утверждает человек.
- Не считать `running`, health API или успех mocked-тестов подтверждением работы всей цепочки. Отдельно проверять настоящий E2E, качество, очереди, backup/restore и мощность. Не обещать встречи/день без полного измерения.
- Образы выпускать одним commit, хранить три immutable digest в release manifest, продвигать те же образы через staging. Не собирать `:local` на production и не обновлять сервисы по отдельности.
- Перед обновлением закрывать приём у оператора, останавливать producers, проверять ВСЕ состояния агента и удерживать queue locks при остановке consumers. При активной записи/AI обработке отложить deploy. Не применять `down -v`, prune или разрушительное изменение схемы к production.
- `create_all` не заменяет миграции. До внедрения Alembic изменения production-схемы проходят вручную по проверенному плану; автоматический CD блокирует несовпадающие колонки. Семантику, индексы и constraints проверять отдельно.
- Секреты calendar_key и токенов хранить вместе с планом восстановления, отдельно от Git и CI; копии должны быть защищены и зашифрованы вне хоста. Не менять общую Ollama/модели/GPU и чужие проекты при обслуживании бота.
- При изменениях обновлять соответствующие инструкции и `docs/implementation-status.md`, различая выполненные проверки и планы. Не активировать production-доставку, пока не настроены окружения и не пройдены критерии приёмки из runbook.

- Правило GPU от владельца (21 октября): будни 07:00–09:00 Europe/Moscow и выходные; перед запуском проверять свободные production-очереди/агента, GPU/Ollama и общий lab.lock. Уступать пользовательской работе; обеспечить watchdog остановки своей нагрузки до границы окна. Расписание: `docs/capacity-schedule.md`; запуск по расписанию через проверенный `scripts/ops/capacity_watchdog.py`, контракт — `docs/capacity-watchdog.md`. Прямой compose run обходит эту защиту.
